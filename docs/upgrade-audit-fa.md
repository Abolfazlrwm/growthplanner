# گزارش بررسی و ارتقای GrowthPlanner

**دامنه:** ارتقای نسخهٔ وب پروژهٔ ارسالی، نه ساخت اپ بومی. بررسی کد، اجرای آزمون‌ها، اصلاح خطاهای تأییدشده، افزودن قابلیت‌ها، راه‌اندازی سرور و آماده‌سازی انتشار انجام شد. پروژهٔ اصلی Django + DRF + HTMX حفظ شده است.

## جمع‌بندی اجرایی

پروژهٔ اولیه پایهٔ خوبی داشت: ورود واقعی، مالکیت داده، هدف و تسک، عادت، دفتر، تقویم شمسی، تمرکز و تست‌های قابل توجه. برای تبدیل آن به پروژهٔ رزومه‌ای قوی، مسئلهٔ اصلی صرفاً زیادکردن صفحه‌ها نبود؛ اتصال امکانات، اعتبارسنجی قابل اعتماد، تجربهٔ کاربری یکدست و استقرار قابل تکرار اهمیت بیشتری داشت.

این ارتقا سه درخواست مشخص را به امکانات عملی تبدیل کرده است: افزودن تسک با جملهٔ طبیعی و پیش‌نمایش قابل اصلاح، فید شخصی قابل ابطال تقویم، و دستیار AI واقعی با رضایت و تأیید. برچسب، زیرتسک و نقطهٔ عطف نیز به مدل‌ها و مسیرهای واقعی متصل شده‌اند. لندینگ و فضای کار بازطراحی شده‌اند و داشبورد از آمار واقعی حساب استفاده می‌کند.

**این محصول هنوز ادعای «تمام امکانات یک SaaS بزرگ» ندارد.** زیرساخت اپ آینده فراهم‌تر شده، ولی اپ بومی، همگام‌سازی آفلاین، اعلان خودکار، همکاری تیمی و چرخهٔ کامل OAuth موبایل در این نسخه نیستند.

## ۱. بررسی پروژهٔ ارسالی

فایل ZIP در مسیر جدا استخراج شد و کد قبل از ارتقا قابل بررسی باقی ماند. فایل `.env` و دیتابیس شخصی داخل بسته به مخزن یا دیتابیس عمومی نسخهٔ جدید منتقل نشدند. هیچ کلید یا رمز موجود در ZIP در پاسخ، فایل مستندات یا سورس عمومی چاپ نشده است.

آزمون‌های پایهٔ موجود ابتدا در SQLite موقت اجرا شدند؛ ۳۵۷ آزمون موفق بود. تعداد قدیمی ثبت‌شده در README با واقعیت آزمون‌ها تطبیق نداشت و مستندات بازنویسی شدند.

| موضوع | مسئلهٔ مشاهده‌شده | اقدام این نسخه |
|---|---|---|
| بستهٔ سورس | حضور تنظیمات خصوصی/دیتابیس در بستهٔ ارسالی | عدم انتقال به مخزن، فایل نمونهٔ محیط بدون اسرار، حفظ نسخهٔ اصلی جداگانه |
| سازگاری دیتابیس | Django 6.1 به MySQL 8.4 نیاز داشت؛ محیط MySQL 8.0 بود | استفاده از Django 5.2.18 LTS، وابستگی pinned و درایور PyMySQL |
| TLS دیتابیس | گزینهٔ TLS به شکل JSON متنیِ غیرسازگار با درایور Python | ساخت SSLContext با بررسی گواهی، رد TLS بدون اعتبارسنجی |
| مهاجرت MySQL | سرور سازگار MySQL، افزودن ستون و FK در یک ALTER را رد می‌کرد | backend کوچک Django با ساخت ستون و FK جدا؛ FK حذف یا ضعیف نشد |
| زمان عادت و تسک | تغییر جزئی ساعت در API و ساعت پایان بدون شروع | اعتبارسنجی وضعیت ادغام‌شدهٔ PATCH و فرم/مدل، خطای ۴۰۰ به‌جای خطای دیتابیس |
| تولید عادت | queryهای اضافی و امکان تولید بازهٔ بسیار دور | مولد محدود روز/بازه، queryهای گروهی و جلوگیری از بازهٔ نامعتبر |
| تکرار جدید | از دست‌رفتن اولویت/برچسب و شروع قبل از روز منتخب | ذخیرهٔ priority/tags/starts_on روی Habit و رعایت آنها در مولد و فید |
| تغییر عادت | رخدادهای ساخته‌شدهٔ آینده می‌توانستند قدیمی بمانند | همگام‌سازی رخدادهای ناتمام آینده؛ حفظ تاریخچه و تکمیل‌ها |
| ویرایش رخداد عادت | ModelForm هنگام validation تاریخ instance را تغییر می‌داد | مقایسه با تاریخ اصلی قبل از validation و جلوگیری از جابه‌جایی |
| کپی تسک | برچسب در کپی از دست می‌رفت | کپی برچسب و زیرتسک‌های مالکیتی؛ زیرتسک‌های کپی از حالت ناتمام شروع می‌شوند |
| خروجی داده | داده‌های جدید/تمرکز در خروجی قدیمی نبودند | JSON نسخهٔ 2.0 با روابط و تاریخچهٔ دستیار، بدون credential و توکن فید |
| بازیابی ایمیل | چاپ کنسولی می‌توانست به‌اشتباه ارسال ایمیل تلقی شود | غیرفعال‌بودن روشن در انتشار فاقد SMTP، بدون وعدهٔ تحویل ایمیل |

## ۲. امکانات تازه و ارتباط آنها

### فضای کار و داشبورد

لندینگ محصول، پیش‌نمایش **صریحاً نمایشی**، ناوبری دسکتاپ، دسترسی سریع روی موبایل، رنگ‌های یکدست و تایپوگرافی فارسی بهبود یافته‌اند. پالت‌های موجود و حالت روشن/تاریک حفظ شده‌اند. داده‌های نمونهٔ لندینگ آمار کاربران یا خروجی واقعی AI معرفی نشده‌اند.

داشبورد، جمع‌بندی تکمیل هفت روز اخیر، دقیقه‌های تمرکز امروز، تعداد عادت‌های فعال، وضعیت روزهای هفته و پیشرفت هدف‌ها را از دیتابیس همان حساب می‌خواند. هدف/عادت/یادداشت/تمرکز قبلی حذف نشده‌اند.

### تسک، هدف و تکرار

برچسب خصوصی، زیرتسک، برد فیلترپذیر، صفحهٔ ویرایش جزئیات و نقاط عطف هدف اضافه شده‌اند. ارتباط‌ها در فرم‌ها و API با مالک حساب بررسی می‌شوند. فیلترهای برد بر دادهٔ واقعی همان کاربر اعمال می‌شوند.

افزودن جمله‌ای، پارسر قطعی فارسی و انگلیسی دارد؛ ارقام فارسی/عربی، تاریخ شمسی عددی و ISO، روزهای هفته، ساعت و مدت، اولویت، هشتگ و تکرار روزانه/هفتگی را استخراج می‌کند. استخراج آزاد تمام عبارت‌های ممکن ادعا نمی‌شود.

پیش‌نمایش **امضای سرور، مالکیت حساب و اعتبار ۳۰ دقیقه‌ای** دارد. هشدارهای واقعی از دادهٔ امضاشده خوانده می‌شوند، نه hidden input قابل دستکاری. حذف متن هشدار در مرورگر الزام تأیید را دور نمی‌زند. اگر پارسر بخشی را نفهمیده باشد، کاربر می‌تواند فیلدها را اصلاح کند و ذخیره کند؛ دکمه برای همیشه قفل نمی‌شود.

### تقویم و فید

نمای ماه/هفته/روز، جابه‌جایی تسک‌های مجاز و دانلود ICS قبلی حفظ شده‌اند. فید جدید با لینک bearer تصادفی، انقضا، چرخش و ابطال عرضه می‌شود. تغییر لینک قبلی را فوراً نامعتبر می‌کند. تنها دارندهٔ لینک معتبر به تقویم آن حساب دسترسی دارد.

فید، گذشتهٔ محدود ۳۰ روزه و آیندهٔ ۳۶۵ روزه تا سقف ۱٬۰۰۰ رویداد را نمایش می‌دهد. پاسخ GET فید تسک در دیتابیس ایجاد نمی‌کند. رخدادهای مجازی و materialized عادت UID یکسان دارند تا تقویم خارجی آنها را دو رویداد مستقل تلقی نکند. UTF-8 folding، CRLF، escape خطوط و زمان UTC از تهران بررسی شده‌اند.

این ویژگی **اشتراک iCalendar** است؛ اتصال OAuth و همگام‌سازی دوطرفه با Google Calendar نیست. سرعت به‌روزرسانی در کلاینت تقویم به تنظیمات همان کلاینت بستگی دارد.

### همراه هوشمند

مدل واقعاً از سرویس سمت سرور فراخوانی می‌شود. یک درخواست زندهٔ مصنوعی و بدون دادهٔ کاربر موفق بود؛ تاریخچه و پیشنهادها در مدل‌های مالکیتی ذخیره می‌شوند. UI پاسخ نمایشی به‌جای خطای سرویس تولید نمی‌کند.

با فعال‌کردن رضایت، حداکثر ۴۰ تسک باز، ۸ هدف فعال و جمع‌بندی عددی هفت روز اخیر ارسال می‌شوند. یادداشت/دفتر روزانه خودکار ارسال نمی‌شود. بدون رضایت، زمینهٔ برنامه اضافه نمی‌شود. متن خود کاربر طبیعتاً برای دریافت پاسخ به مدل ارسال می‌شود.

پیشنهاد هدف و تسک، مالکیت، ساعت، عنوان و تاریخ در سرور اعتبارسنجی می‌شود. تبدیل پیشنهاد به تسک فقط پس از تأیید کاربر است و تکرار تأیید، تسک تکراری نمی‌سازد. حتی اگر تسک پذیرفته‌شده بعداً حذف شود، retry پیشنهاد قدیمی آن را دوباره نمی‌سازد. محدودیت درخواست AI در دیتابیس ثبت می‌شود. timeout، خروجی نامعتبر و نبود سرویس پیام امن دارند.

## ۳. اصلاحات بررسی مستقل

یک بررسی مستقل فقط‌خواندنی، علاوه بر توسعهٔ موازی بخش‌ها انجام شد. ایرادهای واقعی آن قبل از انتشار اصلاح شدند:

1. **Clickjacking:** مجازبودن iframe عمومی به `Content-Security-Policy: frame-ancestors` محدود به خود سایت و originهای مشخص پوستهٔ Manus تبدیل شد. origin جایگزین باید صریحاً در `FRAME_ANCESTORS` تنظیم شود؛ wildcard عمومی مجاز پیشنهاد نمی‌شود. کوکی HTTPS تعبیه‌شده `SameSite=None; Secure` باقی می‌ماند.
2. **تأیید NLP:** warning سمت مرورگر با وضعیت امضاشدهٔ سرور جایگزین شد و اصلاح دستی خطای تحلیل قابل ذخیره شد.
3. **کپی تسک:** برچسب و زیرتسک حفظ می‌شوند.
4. **استقرار Docker:** reliance بر Procfile حذف از ادعا شد. migrations واقعاً پیش از انتشار روی دیتابیس همین پروژه اجرا شدند؛ برای releaseهای بعدی هم اجرای جداگانه لازم است.
5. **مستندات:** ادعاهای قدیمی نسخهٔ Django، دیتابیس، تعداد تست و نقص تکرار حذف شدند.

Schema API تولید و validate شد؛ در اجرای نهایی Schema خطا یا هشدار تولید نشد. فهرست ۳۸ مسیر صفحه از URLconf واقعی ساخته شد و پاسخ HTTP آن دقیقاً با سند JSON مطابقت داشت.

## ۴. شواهد اجرا و محدودیت اعتبارسنجی

مجموعهٔ کامل آزمون‌ها روی SQLite جداگانه اجرا شد؛ توسعه و تست به دیتابیس شخصی ZIP دست نزدند. پس از اصلاحات تکرار، زبان، حساب، تقویم و دستیار نیز ۱۵۵ آزمون مرتبط موفق شدند. نتیجهٔ آخرین اجرای کامل در بخش «نتیجهٔ نهایی» همین گزارش ثبت می‌شود.

روی دیتابیس مدیریت‌شده، migrationها و اتصال واقعی اجرا شدند. سرور Gunicorn آماده شد و `/healthz/`، لندینگ، ثبت‌نام، ورود، CSSها و `manus-routes.json` پاسخ ۲۰۰ داشتند. تست‌های خودکار مالکیت و حالت‌های خطا، جایگزین ادعای آزمایش تحت بار واقعی نیستند.

تشخیص زبان Python/JavaScript/CSS فعال شد، ولی host برخی importهای محیط مجازی Python را resolve نکرد؛ این وضعیت «LSP کاملاً پاک» معرفی نمی‌شود. syntax/compile، system check، migration drift، تست‌های واقعی Django و بررسی syntax JavaScript به‌عنوان شواهد معتبر استفاده شدند.

## مسیر مناسب برای پروژهٔ رزومه‌ای

این نسخه برای ارائه، چند محور مهندسی قابل نشان‌دادن دارد: پارسر دو زبانهٔ تست‌شده، دادهٔ مالکیتی، قرارداد iCalendar، AI تأییدمحور، استقرار Django چنددیتابیسی و مستندات API. به‌جای ادعای «همه‌چیز دارد»، بهتر است همین مسیرهای کامل را در دمو نشان بدهی: ساخت هدف، افزودن تسک با یک جمله، تکمیل زیرتسک، پیشرفت هدف، اشتراک تقویم و پذیرش یک پیشنهاد AI.

قبل از شروع اپ، گام منطقی بعدی، سخت‌سازی عرضهٔ عمومی و تثبیت API است. این کار هزینهٔ بازنویسی اپ آینده را کمتر می‌کند.

## نتیجهٔ نهایی پیش از انتشار

آخرین اجرای کامل: **۴۰۲ تست، ۴۴٫۴۷۰ ثانیه، نتیجه OK** در SQLite موقت. اجرای ۱۵۵ تست مرتبط پس از اصلاح تکرار و دستیار نیز OK بود. `manage.py check` و migration drift بدون ایراد، Schema validate بدون warning/error، و بررسی Python/JavaScript موفق بود. همهٔ migrationهای متعهدشده روی دیتابیس مدیریت‌شده اعمال شده‌اند و HTTP/CSP سرور آماده تأیید شد.

ذخیرهٔ checkpoint و انتشار، مرحلهٔ بعد از این گزارش هستند؛ موفقیت سرور پیش‌نمایش به‌تنهایی انتشار عمومی محسوب نمی‌شود. نشانی عمومی تنها پس از نتیجهٔ موفق نشر در پاسخ تحویل اعلام می‌شود.
